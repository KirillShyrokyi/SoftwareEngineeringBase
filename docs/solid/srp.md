# SRP — Single Responsibility Principle

[← Coupling & Cohesion](../oop/coupling-cohesion.md) · [Roadmap](https://kirillshyrokyi.github.io/SoftwareEngineeringBase/roadmap/)

**Single Responsibility Principle (SRP)** — принцип единственной ответственности.

## 1. Какую проблему решает SRP?

Компонент может работать с одной предметной областью, но при этом совмещать *несколько независимо изменяющихся ответственностей*.

Например, если один класс одновременно рассчитывает налоги по счетам, сохраняет их в базу данных, генерирует PDF и отправляет письма, изменение бухгалтерских правил, технологии хранения и формата документа может независимо затрагивать один и тот же класс.

Ключевой вопрос SRP:

> Какая у этого компонента ответственность и по каким независимым причинам (из-за чьих требований) ему придётся меняться?

Слова «одна причина для изменения» не означают буквально одно возможное техническое изменение. Они помогают объединять изменения, относящиеся к одной ответственности, и отделять изменения, идущие от независимых требований.

## 2. Почему «всё относится к заказам» недостаточно?

```csharp
class OrderService
{
    public void PlaceOrder(Order order) { /* ... */ }

    public void CancelOrder(Order order) { /* ... */ }

    public void GenerateMonthlySalesReport() { /* ... */ }
}
```

Все методы относятся к данным о заказах, но оформление заказов и управленческая отчётность меняются по независимым причинам. Изменение показателей отчёта не должно вынуждать изменять логику оформления заказа.

Возможное разделение:

- `OrderService`: операции оформления и отмены заказа.
- `SalesReportService`: аналитические отчёты.

Компонент отчётности при этом может **читать данные о заказах**, не становясь частью процесса оформления.

## 3. Координация допустима, смешение процессов — нет

Обработка одного заказа может включать проверку склада, сохранение и уведомление покупателя. `OrderProcessor` вправе **координировать** эти шаги: они составляют единый процесс.

Но если в том же `OrderProcessor` появляется метод управления выплатой зарплаты, это уже независимый процесс. Даже если метод только вызывает `IPayrollService`, у координатора возникает чужая ответственность.

**Делегирование не гарантирует SRP**. Необходимо смотреть на ответственность самого вызывающего компонента.

## 4. Нейтральный пример: выставление счёта (Invoice)

Исходная проблема:

```csharp
class InvoiceService
{
    public void IssueInvoice(Invoice invoice)
    {
        // Расчёт налогов и общей суммы
        // Сохранение в базе данных
        // Создание PDF
        // Отправка по Email
    }
}
```

У этих действий разные причины изменения:

| Ответственность | Пример независимого изменения |
| --- | --- |
| Расчёт суммы и налогов | Новые бухгалтерские правила |
| Сохранение счёта | Новый способ хранения |
| Формирование PDF | Новый формат документа |
| Отправка уведомления | Смена Email на другой канал |

Возможное распределение:

- `InvoiceService` координирует последовательность выставления счёта.
- `InvoiceCalculator` рассчитывает налоги и сумму.
- `IInvoiceRepository` задаёт контракт сохранения.
- `PdfGenerator` формирует документ.
- `INotificationSender` задаёт контракт уведомления.

Иллюстративный порядок вызовов после разделения обязанностей:

```csharp
public void IssueInvoice(Invoice invoice)
{
    decimal total = _calculator.CalculateTotal(invoice);
    _repository.Save(invoice, total);

    byte[] pdf = _pdfGenerator.Generate(invoice, total);
    _sender.Send(invoice, pdf);
}
```

Здесь подразумеваются заранее предоставленные зависимости и подходящие методы в их контрактах. Это эскиз ответственности, а не полная реализация со всеми правилами ошибок, согласованности данных и повторных попыток.

Смена оформления PDF в этом варианте затрагивает реализацию генератора. Если его контракт не меняется, логика `IssueInvoice` остаётся прежней.

## 5. Связь с Cohesion и Coupling

- **Cohesion** — логически ли объединены методы и обязанности внутри компонента.
- **Coupling** — насколько компонент зависит от других компонентов и деталей их реализации.
- **SRP** — не объединены ли в одном компоненте независимые области причин изменения.

Интерфейс может уменьшить связанность с конкретной реализацией. Но интерфейс **сам по себе не гарантирует SRP**: координатор по-прежнему может отвечать за несвязанные процессы.

**Не каждый метод требует отдельного класса или интерфейса.** Разделение оправдано там, где проходят реальные границы ответственностей и независимых изменений.

## 6. Подтверждённая mental model и статус

В учебном диалоге продемонстрировано:

1. Расчёт, сохранение, генерация документа и отправка сообщений можно выделить в разные компоненты, оставив общую координацию в сервисе сценария.
2. При независимом изменении формата отчётности не должна изменяться логика оформления заказа.
3. Проверка складских остатков — бизнес-правило оформления нового заказа; сохранение исторического заказа не должно автоматически требовать проверки текущих остатков.
4. При переносе рассуждения с заказов на выставление счетов предложено разделение расчёта налогов, хранения, генерации PDF и доставки документа.

После разбора уточнены типичные ошибки:

- Не считать SRP автоматически выполненным лишь потому, что у класса один метод `Process`.
- Не считать любой «класс-координатор» универсальным местом для несвязанных процессов.
- Не путать интерфейсы и передачу зависимостей с распределением ответственностей.

**Статус: 🟢 Понимаю.** Порог концептуального понимания подтверждён совокупностью рассуждений и переносом подхода в новый пример.

**Статус 🔵 Закреплено:** не подтверждён. Для него нужна более самостоятельная реализация в коде с объяснением выбранных границ ответственности.

## 7. Практика на закрепление

В небольшом учебном приложении самостоятельно реализовать сценарий выставления счёта, отделив расчёт, сохранение и формирование документа, а затем заменить реализацию генерации документа без изменения логики оформления счёта. Объяснить, почему выбранные границы ответственности разумны и не приводят к лишнему дроблению на классы.

Эта практика **предлагается на будущее и не отмечена как выполненная**.
