# Coupling & Cohesion — связанность компонентов и цельность ответственности

[← OOP](index.md) · [Roadmap](https://kirillshyrokyi.github.io/SoftwareEngineeringBase/roadmap/)

## 1. Проблема

Когда программу нужно изменить, важно различать два вопроса:

- **Coupling (связанность компонентов)** — насколько один компонент привязан к деталям другого.
- **Cohesion (цельность ответственности)** — насколько задачи внутри компонента логически относятся друг к другу.

Это разные характеристики. У класса может быть одна понятная ответственность, но при этом сильная зависимость от конкретного способа сохранения данных.

## 2. Coupling: конкретная зависимость мешает замене

```csharp
class OrderService
{
    private readonly FileOrderRepository _repository = new();

    public void PlaceOrder(Order order)
    {
        _repository.Save(order);
    }
}
```

Здесь `_repository` — **поле**, которое хранит ссылку на объект. Вызов `new FileOrderRepository()` внутри сервиса привязывает его к конкретной реализации.

Если хранение заказов меняется с файла на базу данных, потребуется изменить `OrderService`.

### Low coupling через контракт и передачу зависимости

```csharp
interface IOrderRepository
{
    void Save(Order order);
}

class OrderService
{
    private readonly IOrderRepository _repository;

    public OrderService(IOrderRepository repository)
    {
        _repository = repository;
    }

    public void PlaceOrder(Order order)
    {
        _repository.Save(order);
    }
}
```

Теперь внешний код передаёт реализацию `IOrderRepository` через конструктор. Пока контракт подходит обоим способам хранения, основную логику `OrderService` не требуется менять при переходе от файла к базе данных.

Ментальная модель:

```text
Tight coupling:
OrderService -> FileOrderRepository (конкретный тип)

Lower coupling:
OrderService -> IOrderRepository (контракт)
                    ^          ^
                 File...    Database...
```

**Low coupling** не означает «зависимостей нет». Зависимость остаётся, но направлена на согласованный контракт, а не на детали конкретной реализации.

## 3. Cohesion: связаны ли методы общей задачей?

Рассмотрим методы:

```csharp
class OrderService
{
    void PlaceOrder(Order order) { /* ... */ }
    void CancelOrder(Order order) { /* ... */ }
    decimal CalculateTotal(Order order) { /* ... */ return 0m; }
    decimal CalculateSalary(Employee employee) { /* ... */ return 0m; }
}
```

`PlaceOrder` и `CancelOrder` относятся к заказам. `CalculateTotal` тоже может относиться к заказам, хотя выполняет вычисление.

А `CalculateSalary` работает с оплатой труда сотрудников — это другая предметная ответственность. Ему логичнее находиться в отдельном компоненте, например `PayrollService`.

**High cohesion** — методы компонента собраны вокруг логически связанной ответственности. Важно не то, что несколько методов «что-то вычисляют», а то, какую общую задачу они решают.

## 4. Как связаны два понятия

```text
High cohesion
  -> у компонента понятная область ответственности

Low coupling
  -> изменение соседнего компонента реже требует менять этот

Вместе
  -> проще изменять и тестировать систему
```

`Cohesion` описывает **содержимое** компонента; `coupling` — его **связи с другими** компонентами.

## 5. Частые ошибки

- Путать поле `_repository` с методом: поле хранит зависимость, метод вызывает её поведение.
- Думать, что любой метод с расчётом следует переносить в «класс вычислений». Нужно смотреть на ответственность, а не на форму операции.
- Считать, что `interface` вообще устраняет зависимости: он только задаёт иной уровень связи.
- Создавать интерфейс и отдельный класс ради каждого короткого метода без инженерской причины.

## 6. Связи с уже изученным

- **Interface** задаёт контракт между сервисом и реализацией.
- **Composition** позволяет одному объекту использовать другой как компонент.
- **Constructor** позволяет передать компонент при создании объекта.
- **Encapsulation** отвечает за контроль внутреннего состояния, а cohesion — за логическую цельность ответственности.
- Далее эти идеи понадобятся при изучении **SOLID** и **Dependency Injection**.

## 7. Подтверждённая mental model

В учебной диагностике продемонстрировано следующее понимание:

1. При прямом создании конкретного репозитория внутри `OrderService` смена хранения затрагивает сам сервис; передача реализации интерфейса в конструктор уменьшает эту связанность.
2. Работа с заказами и расчёт стоимости заказа логически относятся к одной области ответственности.
3. Расчёт зарплаты не относится к ответственности сервиса заказов. Смешение таких задач ведёт к структурной путанице и усложняет дальнейшее развитие кода.
4. Сам факт вычисления не является достаточной причиной выносить метод из класса: важнее его предметное назначение.

**Статус: 🟢 Понимаю.** Подтверждено в рассуждениях о конкретной зависимости, её замене через контракт, чужой ответственности внутри класса и изменённом условии с вычислением стоимости заказа.

**🔵 Закреплено:** пока не подтверждено самостоятельной практической задачей или самостоятельным применением в коде.

## 8. Для будущей самостоятельной практики

В небольшом примере с заказами создать две реализации `IOrderRepository`, передавать нужную в `OrderService` извне и объяснить, почему смена реализации не требует изменения логики сервиса. Отдельно распределить методы по предметным ответственностям и объяснить выбор.

Эта практика предлагается на будущее; она **не считается выполненной**.
